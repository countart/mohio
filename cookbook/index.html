Letter grade

Turn a numeric score into a letter grade — a reusable task with typed input and check/when branching.

Run it: mio run cookbook/letter-grade.mho

Source

task grade
    take score as int
    returns text
    check score
        when score is more than 89
            give back "A"
        when score is more than 79
            give back "B"
        when score is more than 69
            give back "C"
        otherwise
            give back "F"
    check: done
task: done

call grade with 92 as top
call grade with 74 as mid
call grade with 55 as low

show "92 scores a {{ top }}"
show "74 scores a {{ mid }}"
show "55 scores a {{ low }}"

Output

92 scores a A
74 scores a C
55 scores a F

Reading list

Connect a database, add books, and query the ones you have not read yet.

Run it: mio run cookbook/reading-list.mho (uses SQLite. A plain run keeps its data in a file between runs, so add --memory for a clean database and exactly this output)

Source

connect db as sqlite from env.DATABASE_URL

save to db.books
    title "The Left Hand of Darkness"
    author "Ursula K. Le Guin"
    read "true"
save: done

save to db.books
    title "A Memory Called Empire"
    author "Arkady Martine"
    read "false"
save: done

save to db.books
    title "Piranesi"
    author "Susanna Clarke"
    read "false"
save: done

// Find the books you have not read yet.
find unread in db.books
    where read is "false"
find: done

show "Still to read ({{ unread.count }}):"
repeat each book in unread
    show "  {{ book.title }} -- {{ book.author }}"
repeat: done

Output

Still to read (2):
  A Memory Called Empire -- Arkady Martine
  Piranesi -- Susanna Clarke

Sales by quarter

Filter records to a named date window with timespan — a declared [start, end) range applied inside a find.

Run it: mio run cookbook/sales-by-quarter.mho (uses SQLite. A plain run keeps its data in a file between runs, so add --memory for a clean database and exactly this output)

Source

connect db as sqlite from env.DATABASE_URL

// Q1 2026: January through March (the end date is exclusive).
timespan first_quarter
    start 2026-01-01
    end 2026-04-01
timespan: done

save to db.sales
    product "notebook"
    amount 12
    created_at "2026-02-14"
save: done

save to db.sales
    product "desk lamp"
    amount 40
    created_at "2026-03-30"
save: done

save to db.sales
    product "monitor arm"
    amount 85
    created_at "2026-05-02"
save: done

// Only the rows inside the Q1 window come back (the May sale is excluded).
find q1 in db.sales
    timespan first_quarter
find: done

show "Q1 2026 sales ({{ q1.count }}):"
repeat each sale in q1
    show "  {{ sale.product }}: {{ sale.amount }}"
repeat: done

Output

Q1 2026 sales (2):
  notebook: 12
  desk lamp: 40

Password login

Hash a password, check a login attempt against the stored hash, and grant a role on success — the real, already-built way to log a user in.

Run it: mio run cookbook/password-login.mho (uses SQLite. A plain run keeps its data in a file between runs, so add --memory for a clean database and exactly this output)

Source

connect db as sqlite from env.DATABASE_URL

hash "correct-horse-battery-staple" as stored_hash using bcrypt

save to db.members
    email "alice@example.com"
    hashed_password stored_hash
    role "member"
save: done

// The decoy exists only to be verified against when no account is found, so a
// miss does the same slow work a hit does. Nothing ever logs in with it.
hash "this-value-is-never-anyone-password" as decoy_hash using bcrypt

retrieve.one member from db.members
    match email to "alice@example.com"
retrieve.one: done

// No account with that email finds NOTHING, and finding nothing is a normal empty
// result, not an error. So the test is `is empty`. `on.failure` means the database
// itself went wrong, and putting the not-found message there leaves it never printed
// while the code below reads a member who was never found.
check member
    when member is empty
        // Verified against the decoy purely so this path costs what the other
        // path costs. The answer is the same either way.
        check "correct-horse-battery-staple" against decoy_hash
            on.success
                show "invalid email or password"
            on.failure
                show "invalid email or password"
    otherwise
        check "correct-horse-battery-staple" against member.hashed_password
            on.success
                grant role member.role
                show "login ok, role granted: {{ member.role }}"
            on.failure
                show "invalid email or password"
check: done

Output

4 warning(s) -- run mio check for details
login ok, role granted: member

The four warnings are correct and expected: this recipe hardcodes a password so it can be run without setting anything up, and mio check says so every time. Real code reads it from env.

Session timeout

Lock the page when nobody is there, and let the person back in with a link sent to their email — the browser half and the server half of the same story, both Mohio.

Run it: mio serve cookbook/session-timeout.mho

Source (the client half; the full recipe, server side included, is in the file)

// The browser half. Nobody has moved, typed, scrolled, clicked or touched
// anywhere on this page for 25 minutes, so cover it and ask.
on.idle 25 minutes
    show #relogin
on.idle: done

Output

After 25 minutes of no activity, #relogin becomes visible.
The visitor asks for a link, gets one by email, and the token
in it grants the member role back — see the full file for
the request/new/check handlers that do that half.

Nightly schedule

Declare work that runs on its own, without anyone asking — a named schedule, a time written bare, and the task it runs.

Run it: mio run cookbook/nightly-schedule.mho (uses SQLite. A plain run keeps its data in a file between runs, so add --memory for a clean database and exactly this output)

Source

connect db as sqlite from env.DATABASE_URL

save to db.sessions
    member "ada"
    last_seen "2026-09-01"
save: done

// A schedule is a NAMED declaration. The name is how it is run later.
task expire_old_sessions
    remove from db.sessions
        where last_seen is "2026-09-01"
    remove: done
    give back "expired"
task: done

// The body says WHEN. A time is written bare, never quoted: 09:00, not "09:00".
mioschedule nightly_cleanup
    at 09:00
    timezone "EST"
    run expire_old_sessions
mioschedule: done

// Other timings that run today, one per schedule:
//     every 5 minutes
//     in 30 minutes
//     on december 31 at 11:59pm
//     timeout after 10 minutes
//
// The WEEKDAY forms parse and are NOT WIRED yet -- accepted, and they do nothing:
//     every monday at 9am
//     every day at 09:00
//     on monday

show "A schedule is declared. Run it on demand with:  run mioschedule.nightly_cleanup now"

Output

[mioschedule] registered 'nightly_cleanup' -> tasks=['expire_old_sessions']
A schedule is declared. Run it on demand with:  run mioschedule.nightly_cleanup now

Moving values with a map

A map describes where values go and says nothing about when. It holds chains, and a chain is a line of stages: places a value sits, and shapes it is reformed by on the way.

Run it: mio run cookbook/map-moving-values.mho (uses SQLite. A plain run keeps its data in a file between runs, so add --memory for a clean database and exactly this output)

Source

connect db as sqlite from env.DATABASE_URL

// The shape a value passes THROUGH. It reforms the value and hands it on, which is
// what makes a shape usable as a stage rather than only as a description.
shape tidy
    value as text pad.left to 6 with "0"
shape: done

map Paydata
    data
        order.total -> tidy -> db.ledger.amount
        refund.total -> db.refunds.amount
map: done

create order
    total "42"
create: done

create refund
    total "7"
create: done

// `flow <map>.<chain>` runs ONE chain. The value leaves `order.total`, is reformed
// by `tidy`, and comes to rest in the database.
flow Paydata.order

// `flow <map>` with no chain runs EVERY chain in the map.
flow Paydata

find rows in db.ledger
find: done
find refunds in db.refunds
find: done

show ("padded on the way through: " & rows.first.amount)
show ("the second chain landed too: " & refunds.first.amount)

Output

padded on the way through: 000042
the second chain landed too: 7

Running a map with flow

flow is the verb that makes a map happen — one chain, or every chain in it. It reports nothing while it runs, and check flow asks for where the value came to rest.

Run it: mio run cookbook/flow-run-a-map.mho (no database, no setup)

Source

shape tidy
    value as text pad.left to 6 with "0"
shape: done

map Paydata
    data
        order.total -> tidy -> ledger.amount
        refund.total -> ledger.refunded
map: done

create order
    total "42"
create: done

create refund
    total "7"
create: done

// A destination has to exist before something lands in it, the same as any other
// value in Mohio.
create ledger
    amount ""
    refunded ""
create: done

// ONE chain.
flow Paydata.order
show ("one chain: " & ledger.amount)

// EVERY chain. The first one runs again, harmlessly, and the second one lands too.
flow Paydata
show ("every chain: " & ledger.refunded)

// THE END OF THE CHAIN, which is the question `flow` is usually asked. The endpoint
// is the stage after the last forward hop -- any other position is `grab` or `walk`.
check flow Paydata.order as landed
show ("the endpoint: " & landed)

Output

one chain: 000042
every chain: 7
the endpoint: 000042

Inspecting a map with walk

Where flow runs a map quietly, walk stops at every stage and looks. A transform stage shows an empty value because nothing rests there; what it produced appears at the next place along.

Run it: mio run cookbook/walk-inspect-a-map.mho (no database, no setup)

Source

shape tidy
    value as text pad.left to 6 with "0"
shape: done

map Paydata
    data
        order.total -> tidy -> ledger.amount
map: done

create order
    total "42"
create: done

create ledger
    amount ""
create: done

flow Paydata.order

// Every stage, in order, with what is sitting at each.
walk Paydata.order
    at each stage: report
walk: done

// The two SEMANTIC ends, found by the arrows rather than by counting. `first` is
// where data enters, `last` is where it comes to rest -- the pair to compare when
// asking whether a value survived the trip.
grab first stage from Paydata.order as entry
grab last stage from Paydata.order as exit
show ("entered at: " & entry.name)
show ("came to rest at: " & exit.name)
show ("carrying: " & exit.value)

Output

order [1] order.total (place) = '42'
order [2] tidy (transform) = ''
order [3] ledger.amount (place) = '000042'
entered at: order.total
came to rest at: ledger.amount
carrying: 000042
